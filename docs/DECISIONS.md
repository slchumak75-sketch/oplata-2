## ADR-009. Ручной CRUD операций — в журнале, срок поставки при правке сохраняется
**Дата:** 27.10.2026 · **Статус:** принято (v0.4.0)

- **Контекст:** следующий пункт этапа 2 в ROADMAP — исправление уже
  введённых поставок/оплат и заполнение документа и комментария, которых
  нет при вводе из недельной таблицы и окна «Поставка». Новые правила
  влияния оплат на долг на этом этапе не вводились.
- **Решение:** «Журнал операций» получил добавление, редактирование
  (кнопка или двойной клик) и удаление с подтверждением через
  `dialogs/operation_dialog.py`. Существующая операция правится на месте
  с сохранением `id`; после CRUD журнал вызывает обновление недельных
  таблиц и «Сводки» в главном окне. У «Прихода» виден срок оплаты: правка
  только суммы/документа/комментария сохраняет уже рассчитанный срок, а
  смена типа, даты или контрагента пересчитывает его через существующий
  `calc.payment_due_date`; у «Оплаты» `due_date` пуст.
- **Решение по ячейкам:** если операция дня ровно одна,
  `set_daily_operation` обновляет её сумму на месте, сохраняя документ,
  комментарий и срок. Если операций несколько, сохраняется прежняя
  семантика ADR-006: ячейка задаёт итог дня одной операцией.
- **Последствия:** ошибки ввода исправляются без ручной правки JSON;
  удаление поставки убирает её и из архивного «Долга», потому что исходной
  операции больше нет. Отдельные документы одного дня следует править
  через журнал, а не через ячейку итога дня. Формулы не менялись:
  «Оплата» по-прежнему не уменьшает долг до отдельного ТЗ (ADR-008),
  типы операций пока только «Приход»/«Оплата».

## ADR-008. «Долг» — архивный график: оплата его пока не уменьшает
**Дата:** 27.10.2026 · **Статус:** принято (заменяет FIFO-часть ADR-007)

- **Контекст:** ответ пользователя на предположение v0.3.0: «не надо,
  чтобы из долга исчезала, пусть остаётся для архива. Когда дойдём до
  оплат, то будут разъяснения».
- **Решение:** «Долг» показывает исходные суммы поставок по срокам и не
  меняется от операций «Оплата»; «за неделю» и «на сегодня» суммируют
  те же исходные суммы (`calc.debt_by_due_date`). Никакого распределения
  оплат (FIFO и т.п.) до отдельного ТЗ пользователя не вводить.
- **Последствия:** оплаченная поставка продолжает числиться в «Долге» и
  может попадать в «на сегодня» после срока — это осознанное временное
  поведение до этапа оплат, а не баг.

## ADR-007. Поставка: срок оплаты хранится в операции, долг — FIFO-остаток
**Дата:** 27.10.2026 · **Статус:** принято, в части FIFO/остатка заменено ADR-008

- **Контекст:** пользователь дал макет окна «Поставка» и первые формулы:
  срок = дата + отсрочка (предоплата/реализация — без отсрочки), перенос
  с выходного по календарю «Данные», сумма появляется в «Долге» на срок,
  «за неделю» суммирует долги недели, просроченный долг переходит в
  «на сегодня» на следующих неделях.
- **Решение:** у `Operation` добавлено поле `due_date`, рассчитанное в
  момент ввода (`calc.payment_due_date`), чтобы смена условий поставщика
  позже не переписывала историю; старым операциям срок пересчитывается
  на лету. «Долг» показывает неоплаченный остаток: все оплаты поставщика
  гасят поставки в порядке сроков (FIFO). «На сегодня» — остаток со
  сроком < сегодня; «за неделю» — со сроками внутри показанной недели.
- **Последствия:** распределение оплат и трактовка «сегодня» —
  предположения (SPEC Q1/Q8/Q9), при уточнении пользователем меняется
  только `calc.unpaid_by_due_date` и колонки в `WeekView`.

## ADR-006. Ввод Приход/Оплата хранится как операции дня
**Дата:** 27.10.2026 · **Статус:** принято

- **Контекст:** запрос пользователя — «сделать возможность ввода в поле
  приход и оплата» (+ «таблицу поставщики сделать на всю ширину экрана»).
- **Решение:** сумма в ячейке = итог дня по контрагенту; сохраняется как
  `Operation(kind=Приход|Оплата, date=день, amount=сумма)` в том же JSON.
  Правка ячейки заменяет операции этого типа/дня/контрагента одной;
  пусто/0 — удаляет. Ячейка и строка «ВСЕГО» показывают суммы этих операций.
  «Долг» для ввода закрыт — это будущая формула. Таблица растягивает
  колонки на ширину окна, окно стартует развёрнутым.
- **Последствия:** введённое сразу видно в «Журнале операций» и станет
  исходными данными формул. Ограничение: несколько документов одного дня
  одной ячейкой не выразить — когда появится диалог операций с документами
  (этап 2), семантику правки ячейки нужно пересмотреть.

## ADR-005. Сборка exe — GitHub Actions на `windows-latest`
**Дата:** 27.10.2026 · **Статус:** принято

- **Контекст:** пользователь просил «сборку начинай автоматически на гитхаб средствами экшнс».
- **Решение:** workflow `.github/workflows/build-windows.yml`: тесты на Ubuntu
  (headless Qt) → PyInstaller на `windows-latest` → smoke-test `--self-test` →
  zip-артефакт; по тегу `v*` дополнительно GitHub Release.
- **Последствия:** настоящий Windows-exe собирается без локальной Windows-машины;
  битая сборка отсекается smoke-тестом.

## ADR-004. Демо-данные первого запуска — имена с макетов
**Дата:** 27.10.2026 · **Статус:** принято

- **Контекст:** макеты показывают поставщиков `ааа, ббб, ггг, eee, жжж`.
- **Решение:** при отсутствии `data.json` сидировать именно их (`ггг` с отсрочкой 10,
  как на макете карточки); покупателей и операций — 0, как на макетах.
- **Последствия:** оболочка сразу выглядит «как на макетах»; пользователь удаляет их через карточки.

## ADR-003. PyInstaller: один файл `Oplata.exe` (onefile, windowed)
**Дата:** 27.10.2026 · **Статус:** принято

- **Контекст:** пользователю проще один файл, чем папка с DLL.
- **Решение:** `oplata.spec` — onefile, `console=False`, имя `Oplata`.
- **Последствия:** старт 2–5 с (распаковка во временную папку), размер ~40–60 МБ.
  Если старт/антивирус станут проблемой — переход на onedir + установщик (этап 3).

## ADR-002. Хранение на этапе оболочки — JSON, не SQLite
**Дата:** 27.10.2026 · **Статус:** принято (пересмотр на этапе операций)

- **Контекст:** данных пока почти нет (списки контрагентов + отметки календаря),
  важны прозрачность и лёгкая отладка агентами.
- **Решение:** `DataStore` пишет один JSON (`%APPDATA%\OplataStroymarket\data.json`),
  модель — `AppData` в памяти; экраны не знают про формат файла.
- **Последствия:** при росте операций переезд на SQLite затронет только `storage.py`.

## ADR-001. Стек: Python + PySide6 (Qt), не C#/.NET и не Electron/Tauri
**Дата:** 27.10.2026 · **Статус:** принято

- **Контекст:** нужна программа именно под Windows, похожая на веб-подобные макеты;
  проект будут продолжать разные ИИ-агенты, в т.ч. в Linux-песочницах без Windows.
- **Рассматривалось:** C# WinForms/WPF (нативно, но тесты/сборка логики вне Windows
  сложнее, а агенты в Linux не смогут даже рендерить UI для сверки с макетами);
  Electron/Tauri (тяжёлый рантайм/второй язык, лишняя сложность для локального учёта);
  tkinter (встроен в Python, но вид далёк от макетов).
- **Решение:** Python + PySide6-Essentials. GUI рисуется Qt (на Windows — Segoe UI),
  ядро без Qt тестируется на любом ОС, скриншоты для сверки с макетами снимаются headless.
- **Последствия:** exe собирается PyInstaller-ом (см. ADR-003/005); размер больше,
  чем у нативного .NET, что приемлемо для внутренней программы.
